# Pathment Jitsi deployment and recovery runbook

This directory contains a **sanitized configuration snapshot** of the Jitsi
installation serving `meet.pathment.me`, captured on 5 November 2026.

It is a deployment aid, not a disk image and not a copy of Jitsi source code.
Jitsi is installed from signed Debian packages; copying installed binaries to a
new machine is unreliable. Install fresh packages, then use the snapshot as a
reference when applying Pathment-specific configuration.

## Contents

- `pathment-jitsi-snapshot/SYSTEM-MANIFEST.txt`: OS, capacity and installed
  package versions from the production VM.
- `pathment-jitsi-snapshot/config/`: sanitized Prosody, Jicofo, JVB, Nginx and
  Jitsi web configuration.
- `pathment-jitsi-snapshot.tar.gz`: portable copy of the same snapshot.

No SSH private key, TLS private key, certificate, mentor password, Jicofo
service password or TURN shared secret belongs in Git. Values marked
`REPLACE_AT_INSTALL` must be generated independently for a new deployment.

## Production authentication decision

The current `mentor` username/password is a temporary compatibility measure.
It prevents a guest from becoming moderator merely by joining first, but it is
not the correct long-term identity model for Pathment:

- every mentor shares one security identity;
- it cannot prove that the moderator is assigned to the scheduled session;
- it cannot be revoked for one mentor;
- its use cannot be attributed in an audit log;
- one disclosure compromises every known room.

The production target is **room-scoped, short-lived JWT authentication**:

1. A user signs in to Pathment normally.
2. The Pathment API loads the scheduled session and applies its existing RBAC.
3. Only an assigned mentor/co-mentor/admin receives a host token.
4. The token is limited to the exact Jitsi room and expires in 5–10 minutes.
5. The browser passes the token to `JitsiMeetExternalAPI` as `jwt`.
6. Mentees receive guest access or a room-scoped non-moderator token.

The Jitsi application secret must exist only in the **server deployment's secret
manager/environment**, for example an encrypted production secret in the API
hosting platform. Never put it in Next.js public environment variables, browser
code, Git, the database, logs, or a mobile application. The generated JWT is
short-lived and may be returned to the authorized browser.

Until JWT is implemented, store the temporary mentor password in an
organization password manager with access limited to active mentors. Use one
Prosody account per mentor if the transition will take more than a few days.
Remove the shared account after JWT rollout.

## New-server prerequisites

Use a fresh supported OS. As of this snapshot, Jitsi documents Debian 12+ or
Ubuntu 24.04+ for new package installations. Do not reproduce the current
Ubuntu 20.04 base for a new server.

Before installation:

1. Create a VM and assign a static public IP.
2. Create the DNS `A` record for the meeting domain.
3. Open these OCI security-list/NSG and host-firewall ports:

   | Protocol | Port | Purpose |
   | --- | ---: | --- |
   | TCP | 22 | SSH; restrict source to administrator IPs |
   | TCP | 80 | Let's Encrypt validation and redirect |
   | TCP | 443 | Jitsi web and WebSocket traffic |
   | UDP | 10000 | Jitsi Videobridge media |
   | UDP | 3478 | TURN/STUN |
   | TCP | 5349 | TURN TLS fallback |

4. Verify the DNS record resolves to the new public IP.
5. Preserve the old VM until the new deployment passes the acceptance test.

## Fresh package installation

Follow the current official guide rather than pinning the historical versions
in `SYSTEM-MANIFEST.txt`:

<https://jitsi.github.io/handbook/docs/devops-guide/devops-guide-quickstart/>

At a high level:

```bash
sudo apt update
sudo apt install -y apt-transport-https curl gnupg2 nginx-full
sudo add-apt-repository universe

sudo curl -sL https://prosody.im/files/prosody-debian-packages.key \
  -o /usr/share/keyrings/prosody-debian-packages.key
echo "deb [signed-by=/usr/share/keyrings/prosody-debian-packages.key] http://packages.prosody.im/debian $(lsb_release -sc) main" \
  | sudo tee /etc/apt/sources.list.d/prosody-debian-packages.list

curl -sL https://download.jitsi.org/jitsi-key.gpg.key \
  | sudo gpg --dearmor -o /usr/share/keyrings/jitsi-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/jitsi-keyring.gpg] https://download.jitsi.org stable/" \
  | sudo tee /etc/apt/sources.list.d/jitsi-stable.list

sudo apt update
sudo apt install jitsi-meet
```

Enter the new meeting hostname during package setup and install a Let's Encrypt
certificate using the Jitsi installer. Do not copy TLS keys from production.

## Apply Pathment configuration

Do not blindly overwrite files generated by a newer package version. Diff each
sanitized snapshot file against the newly generated equivalent and transfer the
intent:

- domain and XMPP component names;
- anonymous guest domain;
- JWT/token authentication modules;
- JVB public/private address mapping, if NAT requires it;
- TURN endpoints;
- Pathment web defaults.

For production JWT authentication, follow:

<https://jitsi.github.io/handbook/docs/devops-guide/token-authentication/>

Generate a new application secret:

```bash
openssl rand -hex 48
```

Store that value in both places without committing it:

- the Jitsi Prosody token configuration;
- the Pathment API's protected `JITSI_APP_SECRET` deployment secret.

Recommended Pathment API settings:

```text
JITSI_DOMAIN=meet.pathment.me
JITSI_APP_ID=pathment
JITSI_APP_SECRET=<secret-manager value>
JITSI_TOKEN_TTL_SECONDS=600
```

## Validation and cutover

Validate syntax and services before changing DNS:

```bash
sudo prosodyctl check config
sudo nginx -t
sudo systemctl restart prosody jicofo jitsi-videobridge2 nginx
systemctl is-active prosody jicofo jitsi-videobridge2 nginx
```

Acceptance test:

1. Join a newly generated room as a mentee in an incognito browser.
2. Confirm the mentee waits and does not become moderator.
3. Join through Pathment as the mentor assigned to the session.
4. Confirm the mentor becomes moderator.
5. Confirm a different mentor cannot obtain the host token.
6. Test camera, microphone, screen share and chat with at least three clients;
   two-client testing may not exercise the same bridge path.
7. Verify UDP 10000 from an external network and test one restrictive network
   that requires TURN.
8. Observe CPU, memory, packet loss and JVB bitrate during a representative
   20-person load test.

Only then lower DNS TTL, point the meeting hostname at the new VM, and retain
the old VM long enough for a tested rollback.

## Capacity terminology and current operating envelope

The useful names are:

- **concurrent participants**: everyone connected across all rooms at once;
- **concurrent conferences/rooms**: meetings active at the same time;
- **room size**: participants in one conference;
- **SFU capacity**: the forwarding capacity of Jitsi Videobridge;
- **concurrency limit** or **capacity envelope**: the supported operating limit.

For the current single VM (1 OCPU, 6 GB, 1 Gbps), use this conservative,
unverified operating envelope until a load test establishes a higher limit:

- target: **20–25 concurrent participants total**;
- practical shape: one room of about 20, or two rooms of about 8–12 each;
- soft ceiling: **30 concurrent participants total**;
- do not promise a reliable 49-person room on this VM;
- TURN-heavy usage, screen sharing and many active cameras reduce capacity.

These are planning limits, not a vendor guarantee. Participant count matters
more than room count. Pathment already caps video at 360p and forwards only the
nine most recent video streams (`channelLastN: 9`), while leaving all audio
available. That materially reduces bandwidth, but one OCPU remains the primary
risk. See `docs/VIDEO-CAPACITY.md` for the calculation and monitoring plan.

Current Oracle documentation describes the Always Free Ampere allocation as
2 OCPUs and 12 GB total per tenancy. If no other A1 VM consumes the allowance,
resizing this VM from 1/6 to 2/12 is the first capacity improvement to evaluate.
Confirm the tenancy's live limits before changing the shape.

## Backup policy

Keep three distinct things:

1. This sanitized, version-controlled deployment snapshot.
2. Encrypted secret-manager entries for Jitsi and Pathment secrets.
3. Encrypted infrastructure backups/snapshots for disaster recovery.

Never treat a repository snapshot as a secret backup, and never put an SSH
private key or production password in this directory.
